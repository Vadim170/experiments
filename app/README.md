# BLE Scanner

Простое Android-приложение, которое постоянно сканирует BLE в фоне, подключается
к **подключаемым** устройствам, читает все доступные для чтения характеристики,
привязывает к каждому обнаружению координаты, логирует результат и показывает
список на экране.

## Что делает

1. **Фоновый скан.** Foreground-сервис (`BleScanService`) держит непрерывный
   BLE-скан. Каждые 15 минут скан перезапускается — Android перестаёт отдавать
   результаты «вечных» сканов. Сервис `START_STICKY`, держит `PARTIAL_WAKE_LOCK`
   и поднимается после перезагрузки телефона (`BootReceiver`).
2. **Только подключаемые.** В `onScanResult` отбрасывается всё, у чего
   `ScanResult.isConnectable == false`.
3. **Подключение и чтение.** Найденные адреса складываются в очередь.
   `GattReader` обрабатывает их строго по одному: `connectGatt` →
   `discoverServices` → последовательное чтение всех характеристик с флагом
   `PROPERTY_READ` → `disconnect`. На время сессии скан приостанавливается —
   параллельный скан заметно роняет вероятность успешного коннекта.
   Таймаут сессии — 25 с.
4. **Геопривязка.** `LocationTracker` держит свежую позицию (`LocationManager`,
   GPS + сеть, без Google Play Services), и каждое обнаружение получает
   координаты. Подробнее — ниже.
5. **Логирование.** `BleLogger` пишет в logcat (тег `BleScanner`), в файл
   `Android/data/io.dodo.blescanner/files/logs/ble-YYYY-MM-DD.log` (хранятся
   7 дней) и в кольцевой буфер на 500 строк для вкладки «Лог».
6. **Экран.** Compose: список устройств с индикатором состояния, RSSI, временем
   последнего пакета и последними координатами. Тап по карточке раскрывает точки
   обнаружения и прочитанные характеристики, сгруппированные по службам. Тап по
   координатам открывает их в картах. Вторая вкладка — живой лог.

### Повторный опрос и бэкофф

* успешно прочитанное устройство перечитывается через 15 минут;
* после ошибки повтор через 1/2/3 минуты (по номеру попытки);
* после 3 неудачных попыток устройство откладывается на час.

### Точки обнаружения

Устройство «светится» несколько раз в секунду, поэтому каждый пакет в историю
не пишется. Точка (`Detection`: время, RSSI, координаты) добавляется, когда
выполнено хотя бы одно условие (`DetectionPolicy`):

* это первое обнаружение устройства;
* с прошлой точки прошло ≥ 60 секунд;
* мы сместились на ≥ 25 метров (гаверсинус, `Geo.distanceMeters`);
* координаты появились впервые, хотя устройство уже видели.

Хранится до 50 последних точек на устройство, старые вытесняются. Фикс старше
15 минут считается негодным — лучше честное «координат нет», чем вчерашняя
точка. В карточке видно последние координаты и разброс между первой и последней
точкой, в логе каждая точка пишется строкой `точка <MAC> rssi=… @ <широта,
долгота ±точность>`.

### Расшифровка значений

`Uuids` знает стандартные SIG-овские службы и характеристики (Device
Information, Battery Level, Device Name и т.д.) и разбирает их значения.
Для неизвестных UUID показывается hex плюс эвристика: печатный ASCII →
строка, 1/2/4 байта → число.

## Разрешения

| Версия Android | Что запрашивается |
|---|---|
| 12+ (API 31+) | `BLUETOOTH_SCAN`, `BLUETOOTH_CONNECT` |
| все версии | `ACCESS_FINE_LOCATION`, `ACCESS_COARSE_LOCATION` |
| 13+ (API 33+) | `POST_NOTIFICATIONS` |
| 10+ (API 29+) | `ACCESS_BACKGROUND_LOCATION` — отдельным шагом |

Локация нужна на всех версиях, потому что координаты привязываются к
обнаружениям, поэтому у `BLUETOOTH_SCAN` нет флага `neverForLocation`.

`ACCESS_BACKGROUND_LOCATION` с Android 11 нельзя просить в одном диалоге с
обычной локацией — приложение просит её отдельной кнопкой и уводит в настройки.
Без неё координаты будут проставляться только пока экран включён.

Объявлены и служебные разрешения: `FOREGROUND_SERVICE`,
`FOREGROUND_SERVICE_CONNECTED_DEVICE`, `FOREGROUND_SERVICE_LOCATION`,
`RECEIVE_BOOT_COMPLETED` и `WAKE_LOCK`. Тип foreground-сервиса собирается в
рантайме из фактически выданных разрешений: на Android 14+ `startForeground`
с типом, под который разрешения нет, кидает `SecurityException`.

## Сборка

Общие требования к окружению — в [корневом README](../README.md).

```bash
./gradlew :app:assembleDebug
./gradlew :app:testDebugUnitTest   # юнит-тесты чистой логики
./gradlew :app:lintDebug           # MissingPermission поднят до уровня ошибки
```

APK: `app/build/outputs/apk/debug/app-debug.apk`.

Юнит-тесты покрывают то, что не требует устройства: гео-математику (`Geo`),
правила записи точек (`DetectionPolicy`) и разбор значений характеристик
(`Uuids`). Гео-математика намеренно написана без `android.location`, чтобы
её можно было гонять на обычной JVM.

minSdk 26 — `isConnectable` у `ScanResult` появился в API 26.

## Готовый APK

Собранный debug-APK лежит в репозитории: `../artifacts/blescanner-debug.apk`
(package `io.dodo.blescanner`, versionCode 1, minSdk 26, targetSdk 35).

```bash
adb install -r artifacts/blescanner-debug.apk
```

Подписан отладочным ключом, поэтому для публикации в сторе не годится —
это сборка «поставить и проверить». Артефакт обновляется вручную:

```bash
./gradlew :app:assembleDebug
cp app/build/outputs/apk/debug/app-debug.apk artifacts/blescanner-debug.apk
```

## Ограничения

* Список устройств живёт в памяти процесса: если система убьёт процесс,
  сервис поднимется заново и начнёт сканировать с нуля. История остаётся в
  файлах лога.
* Читаются только характеристики; дескрипторы, notify/indicate и запись
  не поддерживаются.
* Устройства, требующие бондинга или шифрования, отдадут ошибку на чтении
  защищённых характеристик — это фиксируется в логе и в карточке.
* На агрессивных прошивках (Xiaomi, Huawei и т.п.) приложение стоит вручную
  добавить в исключения энергосбережения, иначе фоновый сервис прибьют.
* Координаты берутся от `LocationManager` (GPS + сеть). В помещении первый фикс
  может не прийти вовсе — тогда точки записываются с пометкой «без координат».
* Приложение не тестировалось на живом железе: сборка проверена юнит-тестами и
  lint'ом, реального BLE-прогона на устройстве не было.
